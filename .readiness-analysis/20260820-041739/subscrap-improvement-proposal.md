# Subscrap 상세 개선 제안서

기준일: 2026-08-20  
근거: `best-practice-analysis.md`, `ideal-standard.json`, `readiness-analysis.json`, `docs/PRODUCT_PLAN.md`, `docs/DETAILED_DEVELOPMENT_PLAN.md`  
범위: 제품 개선 제안. 이 문서는 코드·설정·배포·결제·기기 상태를 바꾸지 않는다.

## 1. 제안 요약

Subscrap의 다음 목표는 구독을 ‘찾아 보여 주는 앱’에서 **사용자가 자동 탐지 결과를 이해하고, 해지 뒤 실제 청구 중단까지 확인하는 신뢰 서비스**로 발전하는 것이다.

우선순위는 다음 순서다.

1. 후보 근거 카드 공개 검증
2. 해지 확인·재청구 확인 흐름
3. 계정별 탐색 상태와 설명 가능한 알림
4. 개인정보·지원·운영 경계의 공개
5. 결제·기기·브라우저 실증

이 순서는 ‘새 기능을 많이 추가하는 것’보다 자동 탐지의 오해, 해지 완료 오해, 권한 과신, 운영 불확실성을 먼저 줄인다.

## 2. 현재 위치와 판단

| 영역 | 현재 근거 | 판단 |
|---|---|---|
| 핵심 구독 관리 | 직접 등록·검색·달력·절약 기회·336/336 검사 | 강점 |
| Google 탐지 | Gmail·Play 분리 권한·후보 근거·무시 | 강점, 공개 검증 대기 |
| 해지 | 공식 안내 경로 존재 | 실제 청구 중단 확인이 부족 |
| 품질 | 접근성 8화면 심각 위반 0·가상 1,000명 | 자동 검사 강점 |
| 기기·브라우저 | Chrome·Edge 공개 확인 | Android 화면·iPhone·Firefox·Safari 증거 부족 |
| 결제·운영 | 후보 문서·백업 근거 | 실제 결제·환불·지원·장애 대응 증거 부족 |

Readiness Hub 예비 점수는 복합 40.93이나 증거 완성도는 모바일 4%, 웹 6%다. 따라서 이 제안서는 낮은 점수를 올리기 위한 형식 작업이 아니라, 실제 사용자 위험을 줄이는 순서로 작성했다.

## 3. 제품 원칙

1. 자동 탐지는 추천이며 확정이 아니다.
2. 사용자는 언제나 직접 등록·수정·무시할 수 있다.
3. 해지 안내를 열었다는 사실과 실제 청구가 멈췄다는 사실을 구분한다.
4. Gmail·Google Play가 보지 못하는 카드·Apple·다른 메일 계정 결제는 명확히 알린다.
5. 메일 원문·접근 열쇠·결제자료는 화면·로그·분석 문서에 넣지 않는다.
6. 모든 출시 판단은 자동 검사와 실제 공개 환경 증거를 함께 요구한다.

## 4. 제안 1 — 후보 근거 카드의 공개 완결

### 목표

사용자가 자동으로 나온 항목을 보고 “왜 나왔는지”, “구독인지”, “무엇을 할 수 있는지”를 10초 안에 이해하게 한다.

### 제공할 화면

- 자동 반영 구독: 출처, 탐지 사유, 탐지 날짜, 금액·통화, 신뢰도, 상세 보기
- 확인 필요 후보: 출처, 사유, 날짜, 금액, 신뢰도, `확정·직접 등록`, `무시`
- 범위 안내: Google 자료만 확인하며 다른 결제는 직접 등록할 수 있다는 짧은 문구

### 완료 기준

1. 공개 Pages v0.21.3에서 카드가 보인다.
2. 후보 무시는 사용자 범위에서만 처리되고 다시 나타나지 않는다.
3. 직접 등록은 후보의 이름·금액·통화·주기·날짜를 미리 채운다.
4. 작은 화면과 키보드에서 버튼·상태가 읽힌다.

### 위험과 방어

| 위험 | 방어 |
|---|---|
| 자동 탐지를 확정으로 오해 | ‘확인 필요’·근거·직접 등록 행동을 함께 표시 |
| 일반 구매를 구독으로 오해 | 구매와 반복 결제 후보의 상태·문구 분리 |
| 메일 내용 노출 | 원문 대신 안전한 탐지 사유 코드만 표시 |

### 검증

앱 E2E, Google 서버 검사, 공개 Chrome·Edge 검사, 공개 후 유휴 A56 한 대의 화면 확인.

## 5. 제안 2 — 해지 확인과 재청구 확인

### 문제

공식 해지 안내를 열어도 실제 결제가 멈췄다는 뜻은 아니다. 이 차이를 앱이 분명히 안내하지 않으면 사용자는 절약액과 해지 상태를 잘못 믿을 수 있다.

### 제안 흐름

```text
공식 해지 안내 열기
  → 사용자가 해지 요청을 했다고 표시
  → 확인 화면·확인 메일 보관 여부 기록
  → 다음 결제일 확인 알림
  → 명세서 또는 탐지 결과로 재청구 여부 확인
  → 확인 전에는 “절약 예상”, 확인 뒤에만 “절약 확인” 표시
```

→ 이 그림의 뜻: 앱은 해지를 대신 완료하지 않고, 사용자가 확인해야 하는 다음 행동을 놓치지 않게 돕는다.

### 데이터 상태

| 상태 | 뜻 | 사용자에게 보일 문구 |
|---|---|---|
| 안내 전 | 아직 해지 행동 없음 | 해지 방법 보기 |
| 안내 열람 | 공식 경로를 열었음 | 해지 완료는 아직 확인되지 않음 |
| 요청 표시 | 사용자가 요청했다고 기록 | 확인 화면·메일을 보관하세요 |
| 다음 결제 대기 | 실제 중단 확인 전 | 다음 결제일 뒤에 확인 알림 |
| 중단 확인 | 재청구가 없음 | 절약 확인 |
| 재청구 발견 | 다시 청구됨 | 결제 주체·계정·공식 지원 확인 |

### 완료 기준

- 해지 안내 열람만으로 ‘해지 완료’가 되지 않는다.
- 다음 결제일 전에는 절약액을 확정하지 않는다.
- 재청구가 기록되면 상태가 바뀌고 원인을 확인할 수 있다.
- 저장·복원 뒤에도 상태와 확인 일정이 유지된다.

## 6. 제안 3 — 계정별 탐색 상태와 탐지 한계 설명

### 제안

Google 계정 카드마다 Gmail·Play 연결 여부, 마지막 탐색 시각, 처리 결과 집계, 실패·재시도 상태를 보인다. 단, 메일 제목·주소·원문·접근 열쇠는 보이지 않는다.

### 핵심 문구

> 이 연결은 허용한 Gmail·Google Play 자료만 확인합니다. 카드, Apple, 다른 메일 계정, 영수증 없는 결제는 직접 등록하거나 해당 계정에서 확인하세요.

### 완료 기준

- 연결 전·결과·빈 결과의 세 위치에 같은 뜻의 범위 안내가 있다.
- 각 계정의 결과·작업·연결 해제가 섞이지 않는다.
- 빈 결과를 ‘결제가 없다’고 단정하지 않는다.

## 7. 제안 4 — 설명 가능한 알림과 절약 제안

### 제안

모든 알림과 절약 기회에 `왜 지금 보이는지`, `계산 기간`, `통화`, `기준 금액`, `사용자가 끌 수 있는지`를 붙인다.

| 종류 | 표시할 이유 | 행동 |
|---|---|---|
| 다음 결제일 | 며칠 뒤 얼마가 청구됨 | 일정 확인·알림 변경 |
| 무료 체험 종료 | 자동 갱신 전 남은 기간 | 해지·유지 결정 |
| 가격 상승 | 이전 결제와 현재 결제 차이 | 상세·대안 확인 |
| 중복 후보 | 서비스명·금액·결제일 유사 | 병합·유지 결정 |
| 미사용 후보 | 마지막 사용 기록과 기간 | 유지·해지 검토 |
| 재청구 확인 | 해지 요청 뒤 결제 자료 발견 | 결제 주체 확인 |

### 완료 기준

- 알림에 이유가 없는 경우가 없다.
- 유형별 켜기·끄기와 시점 설정이 있다.
- 알림 권한 거부 상태에서도 핵심 서비스가 정상 동작한다.

## 8. 제안 5 — 개인정보·신뢰 표면 완결

### 필요한 공개 표면

1. 개인정보 처리 목적과 보관·삭제 범위
2. Gmail·Play에서 읽는 것과 저장하지 않는 것
3. 계정 연결 해제 시 사라지는 데이터
4. 데이터 내보내기·삭제 요청 경로
5. 지원 문의 경로와 응답 목표
6. 유료화 전 가격·자동 갱신·환불·복원 고지

### 완료 기준

- 설정 화면에서 개인정보·데이터·지원·버전 정보에 도달할 수 있다.
- 법률 검토나 준수 인증을 받지 않았다면 받았다고 표시하지 않는다.
- 실제 결제 시작 전 가격·환불·자동 갱신 문구와 시험 기록이 있다.

## 9. 제안 6 — 품질·성능·운영 관찰

### 제안

- 현재 336/336 검사를 CI에서 매 공개 후보마다 실행
- 공개 URL의 화면 오류·깨진 링크·서비스워커 판번호 확인
- API p95, 화면 로딩, 탐색 성공·실패, 재시도 수를 집계
- 오류 추적 도구와 임계치 경보 도입
- 백업이 있다는 것뿐 아니라 복원 훈련을 주기적으로 기록

### 초기 목표

| 지표 | 첫 목표 | 근거 수집 방법 |
|---|---|---|
| 공개판 화면 오류 | 0건 | Chrome·Edge·Firefox·Safari 검사 |
| Google 탐색 성공 | 출처별 분리 집계 | 원문 없는 작업 집계 |
| 핵심 API 응답 | p95 목표 문서화 | 운영 서버 측정 |
| 후보 검토 시간 | 기준선 수집 | 익명 사용자 행동 집계 |
| 재청구 확인 완료 | 해지 요청 대비 비율 | 상태 전환 집계 |

## 10. 제안 7 — 실제 기기·브라우저 검증

### 매트릭스

| 환경 | 확인 항목 | 현재 상태 |
|---|---|---|
| Android A56 한 대 | 공개 URL·온보딩·가로 넘침·PWA 설치·업데이트·전체화면 | 연결 확인, 화면 조작 정책 차단 |
| Chrome PC | 공개 URL·서비스워커·오류·1440px | 확인됨 |
| Edge PC | 공개 URL·서비스워커·오류·1440px | 확인됨 |
| Firefox PC | 공개 URL·핵심 흐름 | 미실시 |
| Safari PC | 공개 URL·핵심 흐름 | 미실시 |
| iPhone Safari | 작은 화면·설치·권한 설명 | 미실시 |

### 안전 원칙

Android는 유휴 A56 `R5CY32TNJFM` 한 대만 사용하고, 실제 계정 로그인·구독 추가·결제·설치는 필요할 때만 별도 기록과 함께 수행한다.

## 11. 제안 8 — 유료화 준비

### 결정 전제

실제 결제 제공자, 판매 국가, 사업자 정보, 가격, 무료 체험, 세금, 환불 기준이 확정되기 전에는 결제 기능을 ‘준비됨’으로만 표현한다.

### 샌드박스 검증 목록

1. 신규 구매 승인
2. 카드·수단 거절
3. 동일 요청 중복 차단
4. 무료 체험 종료·자동 갱신
5. 구독 취소
6. 환불
7. 복원
8. 영수증 서버 검증
9. 가격·세금·통화 표시
10. 고객 지원 이관

### 완료 기준

각 결과에 실제 시험 시간, 결과, 사용자 화면, 서버 기록, 되돌리기 방법이 남아야 한다.

## 16. 성공 판단표

| 질문 | 성공 기준 |
|---|---|
| 사용자가 후보를 믿고 판단하는가 | 출처·이유·금액·상태·행동이 한 카드에 있음 |
| 해지 완료를 과장하지 않는가 | 안내·요청·다음 결제 대기·중단 확인 상태 분리 |
| 탐지 범위를 오해하지 않는가 | 세 위치 범위 안내와 직접 등록 경로 |
| 운영 중 문제를 알아차릴 수 있는가 | 오류·성능·탐색 실패·복구 훈련 근거 |
| 상용화가 가능한가 | 결제·정책·기기·브라우저·지원 증거 충족 |

## 17. 결론

Subscrap은 자동 탐지의 근거와 사용자 선택권을 중심에 둔 점이 강점이다. 다음 투자 우선순위는 더 많은 탐지 원천이 아니라, **해지 후 실제 중단 확인**, **탐지 범위의 정직한 설명**, **운영·결제·기기 증거**다. 이 순서로 진행하면 기능 과장 없이 신뢰와 출시 준비도를 함께 높일 수 있다.
